# Windows Gizmos — diagnostic statique borné (D5b)

Aucun plugin tiers, inspecteur, appui, capture ni processus externe lancé. Lecture seule de `%APPDATA%\HotSpot\StreamDock\plugins\com.krabs.windowsgizmos.sdPlugin` (manifest et noms de fichiers) ; aucune lecture de profils utilisateur ni du contenu des scripts de capture. Aucun résultat fonctionnel revendiqué.

## Constats vérifiés

- Manifeste installé : Windows Gizmos 1.0.19, `SDKVersion: 2`, `CodePathWin: bin/streamdeck-batplug.exe`, Windows >= 10. Actions de capture : `com.krabs.windowsgizmos.SnipAndSketchCapturePartOfScreen` et `com.krabs.windowsgizmos.ScreenshotFullScreenSave`, `SupportedInMultiActions: false`, toutes deux avec `PI/Generic_pi.html`. Fichiers correspondants nommés `cmd/com.krabs.windowsgizmos.*.bat` et `cmd/scripts/*Capture*.ps1` / `*Screenshot*.ps1` ; cela ne prouve ni leur invocation ni leur résultat.
- `PI/Generic_pi.html` ne déclare aucun champ de réglage pour ces deux actions ; il charge `common.js`, `common_pi.js`, `index_pi.js`. Le manifeste ne déclare pas de valeurs Settings pour ces actions. Les réglages par instance restent possibles via le protocole, mais aucun réglage requis pour la capture n'est établi par ces seules pièces. Le binaire natif Qt n'a été ni exécuté ni analysé.
- Hôte DeckForge : `plugin_host.rs` passe `-port`, `-pluginUUID`, `-registerEvent registerPlugin`, `-info`, démarre dans le répertoire du plugin, attend le WebSocket `registerPlugin` ; `plugin_runtime.rs` émet `deviceDidConnect`, `willAppear`, `keyDown` et `keyUp`. `ui.rs` traite les réponses et les réglages. Aucune trace du runtime de Gizmos n'a été collectée.
- Comparaison avec https://docs.elgato.com/streamdeck/sdk/references/websocket/plugin/ (référence consultée durant D5b) : les payloads `KeyDown` et `KeyUp` d'une action simple exigent `controller: "Keypad". Avant D5b, `plugin_runtime::event` ne renseignait ce champ que pour `willAppear`, `willDisappear` et `didReceiveSettings` : défaut générique indépendant de l'UUID Gizmos. D5b l'ajoute pour `keyDown`/`keyUp` et étend le test de contrat aux cinq événements. La référence actuelle indique également `resources` dans les payloads ; DeckForge ne le fournit pas : écart SDK restant à qualifier séparément, sans lui attribuer l'échec de capture.

## Hypothèses non démontrées

L'absence précédente de `controller` pourrait affecter un client SDK strict, mais on ne sait pas si le binaire Gizmos le consulte. Ni le démarrage du processus, ni l'enregistrement WebSocket, ni la réception d'un appui, ni la chaîne de capture Windows ne sont prouvés. L'hypothèse d'une dépendance à Stream Dock/FIFINE, à une permission Windows ou à un script reste ouverte. Aucune cause de panne Gizmos n'est établie.

Avec consentement explicite pour l'appui matériel ET les effets de capture, sur copie contrôlée et sans profils personnels : activer `DECKFORGE_PLUGIN_TRACE_UUID=com.krabs.windowsgizmos` avant le lancement de DeckForge ; relever la fiche de prérequis/erreurs, vérifier l'existence du runtime et du handshake, puis demander un unique appui sur l'action concernée et arrêter. Comparer ordre d'envoi `willAppear` / `keyDown` / `keyUp`, réponse ou fermeture de socket, erreurs UI, et sortie effectivement observée par l'utilisateur. Le JSONL `%TEMP%/deckforge-plugin-traces/com_krabs_windowsgizmos-<pid>.jsonl` n'enregistre que sens, nom d'événement et marqueur non pris en charge ; il n'enregistre ni payload ni résultat de capture. Ne pas publier de journaux ou captures sans revue de confidentialité. Si aucun handshake, diagnostiquer d'abord le lancement/prérequis ; si handshake sans `keyDown`, diagnostiquer liaison d'action/entrée ; si `keyDown` arrive sans résultat, distinguer réponse plugin, commande du script et permissions Windows avec l'utilisateur. Aucune de ces étapes n'a été exécutée pendant D5b.
